在“管理后台 → Minecraft → 服务器”打开目标服务器，使用“托管世界备份与恢复”。本页管理该服务器的世界目录，不是 McWeb 数据库、附件和凭据的整站恢复；整站操作见[生产备份、恢复、更新与回滚](/docs/operations/backup-release-rollback/)。

世界恢复会替换服务器当前世界。先安排维护窗口、通知玩家并停止服务器，确保操作期间没有其他人员或外部进程启动它。

## 使用前确认

- 服务器已分配给托管节点，工作目录与世界目录配置正确。
- 节点心跳正常，并报告页面要求的托管备份、世界恢复安全能力；旧版或不兼容节点可能无法使用这些操作。
- 游戏进程确实处于停止状态，不只是网页显示离线。
- 该服务器没有仍有效的恢复计划，节点没有未解决的恢复状态。

页面会列出阻断原因，例如服务器未停止、心跳过期、目录无效或节点能力不足。先解决原因，不要修改记录或跳过检查。

| 操作 | 专用权限 |
| --- | --- |
| 创建托管备份 | `minecraft.world_backups.manage` |
| 规划并执行世界恢复 | `minecraft.world_restores.execute` |
| 处理未决恢复、取消或接管恢复处理方案 | `minecraft.world_restores.resolve_recovery` |

以上操作还需要相应的后台与 Minecraft 模块访问权限。

## 创建托管备份

1. 停止服务器后，选择“创建托管备份”并确认目标。
2. 等待后台任务和节点完成处理，使用“刷新状态”查看进度。
3. 确认备份达到“可用”状态，查看备份编号、创建时间、世界路径、归档大小和清单摘要。

“已请求”“已排队”或“创建中”不等于可恢复备份。失败、隔离或与当前目标不兼容的备份不能用于恢复。页面中的备份记录也不能替代独立保存的整站备份。

## 恢复到所选备份

1. 在“选择并冻结计划”中选择页面列出的可用托管备份，填写恢复原因，然后“冻结恢复计划”。核对服务器、备份编号、世界目录和计划过期时间。
2. 由计划创建者继续操作，输入当前密码；已启用两步验证时，再输入验证码或恢复码，选择“授权当前精确计划”。
3. 阅读覆盖风险，完整输入页面显示的确认文字，然后“执行世界恢复”。授权有时效，不能用于另一份计划。
4. 保持服务器停止，刷新状态并跟踪节点阶段、恢复前备份编号和错误码。

节点会先保留恢复前状态，验证备份及暂存内容，再切换世界。执行前后的检查如果发现备份、服务器配置或节点能力变化，会拒绝沿用旧计划。应重新核对现场情况，不能靠反复点击执行解决。

刷新或重新打开页面后，只有服务端仍允许继续的计划才显示“继续此计划”；继续时需要重新完成身份验证。尚未排队且未过期的计划可由创建者填写原因后取消。已经排队或执行中的恢复不提供同样的取消操作，不能把关闭网页当作取消。

## 判断恢复结果

| 状态 | 下一步 |
| --- | --- |
| 已规划、已授权 | 尚未执行；继续完成授权确认，或在允许时取消 |
| 已排队、执行中 | 等待节点结果，持续保持停机 |
| 已完成 | 检查目标备份和最终世界状态；确认没有启动阻断后再安排启动 |
| 已回滚 | 本次替换未保留，已回到恢复前状态；核对结果后决定后续操作 |
| 失败 | 查看错误码和当前启动阻断状态，不能推断已成功恢复 |
| 需要恢复处理 | 世界状态尚未安全确认，必须进入下述受控流程 |
| 已过期、已取消 | 不能继续执行该计划，需要时重新规划 |

运行中或状态未决时，系统会阻止启动和重启。不要通过修改数据库标记、直接启动游戏进程或另开一份恢复任务绕过阻断。

## 处理“需要恢复处理”

由具备独立高风险恢复权限的人员打开原计划的“受控恢复处理”，保持服务器停止，并根据事故经过和现有证据选择动作：

- “核验并收敛当前已证明状态”：让节点核验已有结果，确认当前可证明的世界状态。
- “继续安装所选备份”：继续以原计划中的备份为目标进行恢复。
- “恢复到恢复前状态”：使用该次操作保留的恢复前状态进行回滚。

填写原因并冻结处理方案，再重新验证身份、输入页面指定的确认文字并排队。方案绑定操作者和当时的计划状态，不是一个立即解除锁定的按钮。

需要交接时，有权限的人员可以对仍处于可取消或可接管状态的方案填写原因并重新验证身份。“接管并重新规划”会保留原记录，为新操作者建立新方案；原授权不可复用。取消方案不会解除原恢复阻断。

只有节点返回的证明被系统确认后，启动阻断才可能解除。仍显示“需要恢复处理”、证明缺失或错误重复出现时，保留服务器、恢复计划、备份和节点操作编号以及错误码，交给运维继续处理。
