# CE 生产就绪缺口与后续开发清单

> 状态：持续实施（真实基础设施自动验收入口已写入但尚未跑通；渠道沙箱、浏览器 E2E 初始截图仍待验收）
> 审计日期：2026-07-29
> 适用范围：McWeb Community Edition（CE）的论坛、商城、公共后台与生产运维

## 版本边界

- CE 不包含 Discord 类空间、频道、频道身份组、频道消息实时分发及其管理界面。
- Discord 类频道功能只属于 EE，相关待办记录在 EE 仓库的
  `docs/ee-chat-production-backlog.md`。
- CE 中其他通知、私信或传输机制不应被命名或包装成 EE 的频道功能。
- EE 是 CE 的下游；CE 的通用修复应先在 CE 完成，再由 EE 合并继承。

## 优先级

- **P0**：不完成就不能对公网或真实资金开放。
- **P1**：可以小范围灰度，但必须在正式发布前完成。
- **P2**：体验、规模和长期维护能力增强。

## 当前已有基础

以下能力已经存在，后续开发应补强而不是重新实现：

- 论坛已有分区权限、主题与回复、审核队列、举报、警告、禁言、慢速模式、
  反重复、发帖限流、全文搜索、附件、投票、私信、通知及较完整的管理后台。
- 商城已有购物车、订单、库存锁、优惠券、礼品卡、站内余额、退款模型、
  履约、会员商品、数字下载及订单事件。
- 管理后台已有细粒度权限检查、模块授权和操作日志基础设施。
- 中英文前端与 Rails 词典键已进入 CI 一致性校验，仍需人工复核关键业务文案。

## P0：论坛

### 1. 发帖与附件必须原子化

当前主题或回复可能已经写入数据库并触发通知等副作用，之后附件绑定失败，
最终却向用户返回失败。需要避免“页面提示失败、内容实际已发布”的状态。

涉及位置：

- `app/services/community/create_topic.rb`
- `app/services/community/create_post.rb`
- `app/services/community/link_post_attachments.rb`

实施要求：

- [x] 在创建内容前完整校验全部附件 ID、所有权、状态和目标可见性。
- [x] 内容创建与附件绑定进入同一事务，或设计明确且可恢复的提交协议。
- [x] 发布通知、积分、Webhook、订阅等副作用只能在内容和附件成功提交后执行。
- [x] 客户端重试不得产生重复主题、回复或重复副作用。

验收标准：

- 无效、越权、已绑定和部分有效附件均不会留下可见内容。
- 数据库异常或事务回滚后没有通知、积分、Webhook 和孤立关联。
- 并发重试只产生一份用户可见结果。

### 2. 上传安全链路

当前上传校验主要依赖文件名、扩展名和客户端提交的 MIME 类型，不能作为公网
文件安全边界。

实施要求：

- [x] 根据文件魔数和实际解码结果识别类型，不信任客户端 MIME。
- [x] PNG/JPEG 完整解码后生成新字节，限制边长、总像素和输入/输出字节，并拒绝
  畸形、拼接及尾随载荷。
- [x] 对可下载附件提供病毒扫描/恶意文件扫描接口和隔离状态。
- [x] 明确 SVG、HTML、脚本、压缩包和可执行文件策略。
- [x] 增加用户、身份组和站点级容量、数量及频率配额；现行边界和并发预留协议见
  [`ATTACHMENT_SECURITY.md`](ATTACHMENT_SECURITY.md)。
- [x] 自动清理过期、未绑定和隔离失败的 Blob。
- [x] 下载响应设置安全的 Content-Type、Content-Disposition 和
  `X-Content-Type-Options: nosniff`。

验收标准：

- 伪造扩展名/MIME、压缩炸弹、畸形图片和未授权附件下载均有自动测试。
- 上传失败不会留下永久 Blob。
- 私密分区附件不能通过直链、搜索、缓存或对象存储地址泄露。

### 3. 公网滥用与规模验证

- [x] 为注册、登录、搜索、预览、上传、发帖、回复、反应、举报和私信建立统一
  的账号/IP、资源及操作组合限流策略。
- [ ] 如确有产品和合规需求，再增加设备维度；现行代码不采集浏览器指纹，也不把
  设备限流误报为已实现。
- [x] 限流响应返回可用的 `Retry-After`，并可在后台配置及观测。
- [x] 对 PostgreSQL 全文搜索、搜索建议、热门榜单、未读统计和通知聚合执行
  查询计划审查；现行基线与脱敏复核方法见
  [`COMMUNITY_QUERY_PLAN_OPERATIONS.md`](COMMUNITY_QUERY_PLAN_OPERATIONS.md)。
- [x] 建立匿名、普通会员、受限会员、版主和管理员的权限回归矩阵。
- [ ] 完成桌面端、窄屏移动端、长文本、大图片和空数据组合测试。

最低验证场景：

- 普通浏览与搜索压力测试。
- 热门主题集中回复压力测试。
- 大量未读、通知和订阅用户场景。
- 私密分区、隐藏主题、待审核内容和悄悄话无越权泄露。

## P0：商城

### 1. 实现真实支付渠道

`app/services/payments/stripe_provider.rb` 当前仍是模拟实现：它没有调用 Stripe
创建真实 Checkout Session/PaymentIntent，退款也没有调用真实退款接口。

实施要求：

- [x] 使用官方 SDK 创建真实支付会话或 PaymentIntent。
- [x] 金额和币种只取自服务端订单快照，不能采用客户端值。
- [x] 创建支付时使用稳定的幂等键，并保存真实 provider payment/session ID。
- [x] 生产环境严格拒绝 `fake` 渠道，即使用户直接伪造请求参数。
- [x] 仅允许后台已启用且配置完整的支付渠道。
- [x] 处理支付失败、取消、超时、异步支付和晚到支付。

### 2. Webhook 与支付确认

- [x] 对原始请求体执行官方签名验证，并限制请求体大小。
- [x] 明确允许处理的事件类型；未知事件只能记录，不能改变订单。
- [x] 校验支付对象、订单、金额、币种和环境（test/live）完全一致。
- [x] Webhook 事件以 provider + event ID 保证数据库级幂等。
- [x] 建立失败重试、死信、人工重放和“处理中超时”恢复机制。
- [x] 晚到的已付款订单进入独立人工处理队列，不能只写日志。

### 3. 真实退款与崩溃恢复

- [x] 调用真实支付渠道退款 API，并保存 provider refund ID、状态和错误码。
- [x] 每次退款使用稳定幂等键。
- [x] 解决“渠道已退款，但进程在本地提交前崩溃”的恢复问题。
- [x] `approved` 状态必须可超时重领、查询渠道状态或人工恢复，不能永久卡住。
- [x] 部分退款、累计退款、全额退款、重复回调和并发退款保持金额守恒。
- [x] 库存、礼品卡、余额、优惠券、会员资格和数字权益恢复可重入。

### 4. 支付后台与对账

- [x] 增加支付渠道配置页，敏感凭证加密保存且永不回显完整值。
- [x] 增加支付连接测试及 Webhook 配置检查。
- [x] 增加支付记录、Webhook 事件、孤儿/晚到支付、退款和失败任务查询页。
- [x] 增加日对账任务，对比本地订单与渠道支付/退款结果，并提供差异复核闭环。
- [ ] 所有人工标记支付、退款、余额调整和权益恢复都写入不可变审计日志。
- [ ] 高风险动作要求单独权限和二次确认。

## P1：身份生命周期

归属：以下能力由 CE 提供，因为登出、邮箱所有权变更、账户关闭和个人数据导出都属于
所有版本共用的身份与隐私基础设施。下游功能只能通过已声明的贡献器注册自己的模块，
不得复制核心流程或把产品语义带入 CE。

- [x] `P1-01` 登出使用明确的整页导航契约：普通请求返回安全公共页重定向，Inertia
  请求返回 `X-Inertia-Location`；前端无论成功、网络失败或回调异常都终止 loading，
  并以整页导航落到安全公共页。验收覆盖普通请求、Inertia 请求、会话清除、失败回退
  和跨应用重定向，不依赖当前产品首页。
- [ ] `P1-02` 邮箱修改先创建唯一、限时的 pending email 请求，仅在新邮箱确认后原子
  切换；新旧邮箱都收到不含敏感日志的通知，旧邮箱持有限时撤销链接。验收覆盖重复与
  并发申请、目标邮箱占用、确认/撤销过期、旧请求失效、确认后其他会话撤销、当前会话
  身份刷新，以及确认或撤销的幂等性。
- [ ] `P1-03` 账户关闭通过通用 lifecycle contributor registry 执行预检、执行和逆序
  补偿；CE 自带 authored-content contributor，其他模块只能注册通用贡献器。验收覆盖
  预检阻塞、部分执行失败后的补偿、重复调用、最后站主保护，以及逐模块持久化结果和
  审计说明。
- [ ] `P1-04` 数据导出通过 contributor registry 生成版本化 manifest；每个模块声明
  稳定键、文件和记录数，CE 现有导出迁入内置贡献器。验收覆盖注册冲突、模块失败后
  可重试、manifest 版本与逐模块计数、敏感字段排除、所有历史记录的游标分页，以及
  重试不创建新的逻辑申请。
